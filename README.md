# Game

Grid based, turn based, zero sum, 2 player strategy game. Players compete to build ports and ships while destroying the enemy's, with the eventual goal of capturing their home port. Used as a sandbox to experiment with machine learning in inperfect information games. 

# Rules

## Combat 

A port is captured by positioning a LANDING ship on a water tile adjacent to an enemy port and issuing a `CapturePortAction`. Ship vs ship combat is resolved as a binary outcome (ship is alive or dead, no damage model). Each ship type has a cost, strength, attack range, speed, visibility coefficient, and scouting coefficient

A ship can attack any spotted enemy ship within its attack range on a given turn. Ships can move before attacking. When a player attacks, a probability of kill is calculated based on the relative strength of the attacker and defender, as well as a modifier based on each ship's type. The probability distribution is sampled, and the defending ship is deleted if destroyed. 

Detection range for two ships is calculated as the product of each's visibility coefficient and scouting coefficient. High visibility coefficients mean the ship is larger and will be more easily spotted by the enemy, while a higher scouting coefficient increases the detection range 

## Economy

Each turn, every port a player owns generates 25 raw materials. These raw materials are transformed into cash if the materials are transported to the home port by transport ships (capacity 100 raw materials per ship). A player is free to spend as much of their cash as desired per turn, or save for the next turn. Cash generated by a transport ship landing at the home port is available to spend on the current turn. 

Enemy ports are captured by positioning a LANDING ship adjacent to the port and issuing a `CapturePortAction`. New ports are built by positioning a BUILDER ship adjacent to an empty land tile and issuing a `BuildPortAction` targeting that tile; the builder is consumed and the tile becomes a new port owned by the buyer.

## Map

All distances are measured as manhattan distance. A simple yaml config is used to define top level map params, then a map is randomly created and stored in a json 

## Ship Types

- **Carrier, Battleship, Cruiser, Destroyer, Submarine** — combat ships.
- **Merchant** — transport. Carries up to 100 raw materials at a time; delivers cash when landing at the home port.
- **Landing** — captures enemy ports. While on a water tile adjacent to an enemy port, can issue a `CapturePortAction` targeting that port to flip its ownership.
- **Builder** — single-use. Move it to a water tile adjacent to empty (un-ported) land, then issue a `BuildPortAction` targeting that land tile. The builder is consumed and the tile becomes a new port owned by the buyer.

## Conventions

- **All distances are Manhattan distance** — movement, attack range, detection range, and build adjacency. "Adjacent" means Manhattan distance 1 (the four cardinal neighbors).
- **Ships exist only on water.** No ship ever occupies a land or port tile. All interactions with land (building a port, capturing a port, loading/unloading materials at a port) are performed via actions issued from an adjacent water tile. Ship type determines which of these actions are legal: LANDING can capture, BUILDER can build, MERCHANT can transfer materials.

## Building Ships

A player issues a `BuildShipAction` specifying:
- the friendly port to build at,
- the spawn tile (must be adjacent to that port, in bounds, water, and unoccupied),
- the ship type to build.

The action succeeds if the player owns the port, the spawn tile is legal, and the player can afford the ship's cost. Cost is deducted and the new ship appears at the spawn tile.

## Game Startup

At the start of every match:

1. **Map** — generated from `mapConfig.yaml` into `map.json` (random ports + land per player area). Each player additionally receives a fixed home port:
   - Player 0 home: `(0, 0)`
   - Player 1 home: `(width - 1, height - 1)`
2. **Starting cash** — both players begin with 250 cash.
3. **Starting ships** — none. Players must purchase their initial fleet from their starting cash on turn one.
4. **Turn order** — Player 0 acts first.

## Turn Mechanics

- Players take sequential turns. A turn ends when the current player issues an `EndTurnAction`.
- Movement is **per-tile**: each `MoveAction` advances one ship by one tile (4-directional). A ship can be moved up to its `speed` value worth of tiles per turn, across any number of `MoveAction`s. The agent receives a fresh observation after each tile, so it can react to newly-spotted enemies mid-traverse.
- A ship's `tiles_moved_this_turn` counter resets at the end of *its owner's* turn (not the opponent's).
- Ships can move and attack in either order within a turn.

# Setup

Python 3.11+. Poetry installs everything except the torch wheel. On the RX 7700 XT / 7800 XT, install the ROCm wheel after `poetry install` (ROCm reports the GPU as `torch.cuda`):

```bash
poetry install
poetry run pip install torch==2.10.0 \
    --index-url https://download.pytorch.org/whl/rocm7.0 \
    --force-reinstall --no-cache-dir
```

If `torch.cuda.is_available()` stays false on gfx1101, export `HSA_OVERRIDE_GFX_VERSION=11.0.0` before training. A CPU-only wheel is fine for tests and smoke runs; pass `--device cpu` or set `device: cpu` in the smoke configs.

`runs/` and `**.json` are gitignored. Maps used by training and by the engine tests are generated at runtime. `pytest` writes `battleboats/core/config/map.json` only when that file is missing, so a local map is left in place.

```bash
poetry run pytest
poetry run pytest -o addopts= -m slow   # god-mode MCTS benchmark
```

The C++ port under `cpp_core/` is a skeleton (`game_engine.cpp` and `map.cpp` are empty). The Python engine is the source of truth.

# Play against an agent

Local page, one game at a time. Pick a side and an opponent: random, the full-information scripted baseline, or any `.pt` checkpoint under `--checkpoint-dir`.

```bash
poetry run python scripts/play_vs_agent.py --checkpoint-dir runs --port 8765
```

Open the printed URL (`http://127.0.0.1:8765` by default). Fog of war applies to the human. The scripted opponent is labeled as full information. A checkpoint uses the same masked policy as training. `--device auto` picks the ROCm GPU when the wheel can see it.

# Skill curriculum

Each skill trains on 2×3, then 3×3, then 4×4. The promoted checkpoint is the next stage's warm start. Skills, in order: merchant (throughput), landing (capture), combat (destroyer vs a strength-0 merchant), builder (build the marked land tile). The last stages are the full game on 6×6 (vs random) and 8×8 (vs a refreshed snapshot of the learner). Full-game promotion is win rate against a random opponent. Reward shaping stays inside the minigames; the full game stays sparse ±1.

```bash
poetry run python scripts/train_curriculum.py --config configs/curriculum.yaml
```

Smoke (one update per stage, CPU, missed gates still hand off):

```bash
poetry run python scripts/train_curriculum.py --config configs/curriculum_smoke.yaml
```

Resume is on by default (`runs/curriculum/state.json`). `--no-resume` starts over. `--allow-unmet` hands a checkpoint on even if the gate is missed; otherwise the process exits 2. `--init-checkpoint` warm-starts stage 0. `--device auto` overrides the yaml.

Checkpoints are `{model_state, model_config}` only. They do not store an opponent id or a rating, so a later quality-diversity run can load `runs/curriculum/latest.pt` directly.

# Self-play

After the curriculum, train the full game against the last few snapshots. Most games sample that ring uniformly. A fraction (`random_opponent_frac`) are vs a random agent so the value head still sees decisive games. This is not a league: no Elo, no PFSP, no exploiters. `RecentSnapshots.sample` is the function a quality-diversity archive would replace.

```bash
poetry run python scripts/train_selfplay.py --config configs/selfplay.yaml
poetry run python scripts/train_selfplay.py \
    --config configs/selfplay_smoke.yaml \
    --init-checkpoint runs/curriculum_smoke/latest.pt
```

The real config looks for `runs/curriculum/latest.pt` and falls back to a random policy if that file is missing.

Rollouts are single-process Python, so the RX 7700 XT / 7800 XT spends most of a run idle: the network is a small transformer (`d_model` 64) and `enumerate_legal` is the cost. On a CPU-only VM, one merchant update of 256 decisions on a 4×4 board took about 1.1 seconds, and one full-game update of 128 decisions on 6×6 took about 0.4 seconds, both while fleets were still tiny. `configs/curriculum.yaml` is about 1.0 million decisions and `configs/selfplay.yaml` about 0.4 million. At that early-game rate the curriculum is on the order of an hour; games that grow real fleets on 8×8 will be slower, so expect a few hours of wall clock on the 16-thread box rather than a GPU-bound run. The 16 CPU threads are unused by these scripts.

```bash
poetry run python scripts/eval_agent.py \
    --checkpoint runs/selfplay/latest.pt --opponent scripted --games 40
```
